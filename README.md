# ci-workflows

Reusable GitHub Actions workflows and actions for Mobiweb Expo projects. A project keeps thin caller files in its own `.github/workflows/` and calls the shared workflows here:

```yaml
jobs:
  ci:
    uses: Mobiweb-Studio/ci-workflows/.github/workflows/ci.yml@v1
```

The repository is public so that projects in other GitHub organisations can call it. It holds CI logic only: no app code, no docs and no secrets. Secrets and environments stay in each project.

## Using it

1. Copy the caller files from [`examples/callers/`](examples/callers) into the project's `.github/workflows/`. Keep each file's job id: a called job reports as `<caller job> / <shared job>`, so `ci` reports `ci / checks`, `ci / commits`, `ci / secret-scan` and `ci / ticket-key`, and the device gate waits for those names. Add the names you want to require to the main branch's ruleset.
2. Set the inputs. Every input and the token permissions the caller must grant are listed in the header comment of the workflow, and the caller examples already set them. A caller sets only inputs and secrets. It also owns its triggers, path filters, concurrency groups and token permissions. To change what a workflow does, add your own jobs in a separate workflow file; do not edit the steps of a shared one.
3. Give each caller job the permissions its example grants. A called workflow can only narrow the caller's token, so a caller that grants less fails at startup.
4. Create the repository secrets the callers pass by name: `CLAUDE_CODE_OAUTH_TOKEN` (the QA agent), `JIRA_API_TOKEN` (Jira evidence, only when used), `MS_TENANT_ID`, `MS_CLIENT_ID` and `MS_CLIENT_SECRET` (Jira evidence stored on OneDrive, only when used), `EXPO_TOKEN` and optionally `SENTRY_AUTH_TOKEN` (release and hotfix), optionally `RELEASE_PLEASE_TOKEN`, and optionally `NPM_AUTH_TOKEN` (for a project with private packages on GitHub Packages: `ci`, `device-checks`, `native-cache`, `ios-regression`, `release` and `hotfix-ota` set it in the environment of the jobs that run `pnpm install` and write `//npm.pkg.github.com/:_authToken=${NPM_AUTH_TOKEN}` to the runner's `~/.npmrc` (the iOS jobs to a user-level `.npmrc` under the runner's temp folder), because pnpm does not expand environment variables in the credentials of a project `.npmrc`; without it nothing changes), and optionally `MAESTRO_ENV` (the Maestro flows' variables, such as a test account for flows that sign in against a real backend: one `MAESTRO_<NAME>=<value>` per line, without quotes; `device-checks` and `ios-regression` give it to their Maestro jobs, and `device-checks` to the QA agent too; `scripts/ci/maestro-env.sh` masks each value in the log, exports the variables, and replaces the values with `***` in Maestro's debug output and reports and in the agent's output before they are uploaded, because those hold the typed text. The agent types a value with `qa-fill-secret <@ref|selector> <MAESTRO_NAME>` (`scripts/agent-qa/bin`), so it never sees it; the project's `scripts/agent-qa/instructions.md` or `qa-notes.md` tells it which variable to use). A caller job cannot declare an environment, and an environment's own secrets do not reach a called workflow, so these are repository secrets, readable by every workflow in the repository but not by fork pull requests. The shared jobs still declare the environments `qa-agent`, `jira-evidence` and `production-release`: create them in the project, and use their required reviewers and branch rules as the approval gates. `secrets: inherit` is not used, because it only works inside one organisation.

## The workflows

| Workflow | Caller job id | What it does |
|---|---|---|
| `ci.yml` | `ci` | Commit messages, secret scan, types, lint, tests, layout, dead code, and the Jira ticket key when asked. |
| `docs-check.yml` | `docs-check` | Requires docs for feature changes unless the PR has `no-docs`. |
| `human-review.yml` | `human-review` | Needs a person's approval of the head commit unless an agent review of it exists and the `needs-human-review` label was never applied. Off until a project's calibration is signed off: set `HUMAN_REVIEW_ENABLED` to `true`. |
| `device-check-mode.yml` | `device-check-mode` | Keeps one PR comment that says whether the two device checks run and why. |
| `device-checks.yml` | `device-checks` | Maestro and the QA agent on one shared APK, Maestro on an iOS simulator when asked, then the Jira evidence. |
| `native-cache.yml` | `native-cache` | Seeds the APK and build caches on main, and the iOS simulator app when asked. |
| `ios-regression.yml` | `ios-regression` | On a schedule on main, every Maestro flow on each iOS runtime asked for: tagged flows that fail, and untagged ones that pass. |
| `android-regression.yml` | `android-regression` | On a schedule on main (the example: every night), every Maestro flow on an Android emulator, `nightly` ones included. |
| `jira-evidence-merge.yml` | `jira-evidence-merge` | Attaches the last device-check screenshots to the Jira ticket when the PR merges, or stores them on OneDrive and links them. |
| `release.yml` | `release` | release-please, then the store build and submit when a release PR merges. |
| `hotfix-ota.yml` | `hotfix` | A JS-only production update, started by hand. |

`ci` takes `fsd`, `dead-code` and `vendor-isolation`, true by default, for a project that declined that module; a step that is on and whose script is missing fails. `device-checks` also takes `maestro` and `qa-agent`, both true by default, so a project that declined a device check passes false and that check never runs. It also takes `qa-agent-max-turns` and `qa-agent-max-budget-usd`, 40 and 0.50 by default, for a project that gives the QA agent more room. Every workflow takes a `runner` input. The jobs that build, test or run the app default to the Blacksmith label the boilerplate uses; a project without Blacksmith passes its own label, and the emulator jobs need KVM and a large disk. The jobs that only read, wait or comment run on `ubuntu-latest`, a GitHub-hosted runner, so a job of a few seconds does not cost a billed Blacksmith minute: `commits`, `secret-scan` and `ticket-key` in `ci`, and `changes`, `gate`, `ios-app-link` and `jira-evidence` in `device-checks`, through a `light-runner` input; `device-check-mode`, `docs-check`, `human-review` and `jira-evidence-merge` through their `runner` default. A project that cannot use GitHub-hosted runners passes its own label to both.

`device-checks` runs only the Maestro flows a change affects when the project has `.maestro/IMPACT`: one line per rule, as in CODEOWNERS, a path glob from the repository root and the flow tags a change there affects (`src/pages/login/** login`; a tag `*` means every flow). The flows tagged `smoke` always run. Every flow runs when the project has no map, on a story PR (label `us`), or when a changed app file matches no line, so the map can narrow a run but never hide a change it does not know. The mode comment names the tags. Flows tagged `nightly` run only in the regression workflows. Each flow writes its screenshots to `maestro-output/<flow>/`, and the evidence on OneDrive names the files `android/<flow>/…` and `ios/<flow>/…`, beside a `summary.md` with each flow's result. `run-maestro.sh` lists the flows it ran in `maestro-output/flows.tsv`, and the Jira comment turns that into a table: each flow's `name:` linked to its file at the PR's head, its result on Android and iOS, and the acceptance criteria its tags name, written `<KEY>-AC<n>` (such as `ICLIGO-22-AC4`, shown as "ICLIGO-22 AC 4").

`device-checks` also takes `ios-runner`, empty by default. When a project names a runner there (a JSON array of labels for a self-hosted Mac, such as `'["self-hosted","macOS","ARM64","ios"]'`, or a hosted label such as `macos-15`), the `maestro-ios` job gets the app for the iOS simulator on it, runs the flows whose config has the tag `ios` on a simulator made for the job, and keeps the zipped simulator app as the artifact `ios-simulator-app` for 7 days; the `ios-app-link` job then comments its link on the PR, so a reviewer with a Mac can open the PR in the Simulator. The app is built for the simulator ad-hoc signed (the identity `-`, no certificate or Apple account), so it carries the entitlements prebuild generates and can use the Keychain, as `expo-secure-store` needs. Like the APK, the app is repacked with the PR's JS (about 25 seconds) when a cached app has the same native fingerprint, and built when none has; a repacked app is signed again ad-hoc with the same entitlements: pass the same `ios-runner` to `native-cache`, whose `seed-ios` job fills that cache from main. When `jira-evidence` is on, the Jira comment gives the iOS verdict too, and the screenshots of a failed iOS run. The runner needs Xcode, CocoaPods and Java 17, and a GUI session for the simulator. The job runs only for PRs from the same repository, and its only secrets are the optional `MAESTRO_ENV` (redacted from Maestro's output, so none stays on the Mac's disk) and the optional `NPM_AUTH_TOKEN`, which the job writes to a user-level `.npmrc` under the runner's temp folder (emptied after each job), never to the Mac's own `~/.npmrc`. The caller example passes the repository variable `IOS_RUNNER`. `ios-regression` runs on the same runner on a schedule: every flow, tagged or not, on each runtime in its `runtimes` input (installed on the runner), one at a time. A flow tagged `ios` that fails fails the run; an untagged one that passes is listed in the summary as one to tag. It refuses any event but `schedule` and `workflow_dispatch`, so pull request code never reaches the runner through it.

`device-checks` and `jira-evidence-merge` post the Jira evidence to the ticket in the branch name by default. A project that tracks its device checks on a QA sub-task of each story passes `jira-evidence-target: qa-subtask` to both. The poster then reads the branch's ticket, takes its parent when it is a sub-task, and posts the comment and screenshots to the story's one sub-task with the label in `jira-qa-label` (`qa` by default). When the story has no such sub-task, or more than one, or Jira cannot be read, the evidence goes to the branch's ticket and the job shows a warning that names the reason. The Jira account needs no more than before (Browse Projects, Add Comments, Create Attachments): a person makes the QA sub-task, and the poster never creates or edits an issue.

A project whose Jira site is short of attachment storage passes `jira-evidence-storage: onedrive` to both, with `onedrive-drive-id` (a SharePoint or OneDrive document library's drive id) and `onedrive-folder` (the folder in it, such as `ICligo/QA evidence`), and the secrets `MS_TENANT_ID`, `MS_CLIENT_ID` and `MS_CLIENT_SECRET`. The poster then gets a Microsoft Graph token with the client-credentials flow and uploads the screenshots and `qa-report.json` of every run, passing runs too, to `<folder>/<story>/<ticket>/PR-<n>/<run id>-attempt-<k>/`, and on merge to `PR-<n>/merged/`. A file over 4 MiB goes through an upload session. The comment links the folder with a view-only link for the organization, never an anonymous one, or with the folder's own address and a warning when the tenant refuses such links. Every Microsoft failure is a warning too: the comment is still posted and says the evidence could not be stored, and the poster does not fall back to Jira attachments. The app registration needs only the application permission `Sites.Selected`, with the `write` role granted on the one site by a SharePoint administrator, never `Files.ReadWrite.All` or `Sites.ReadWrite.All`. The Jira account then needs only Browse Projects and Add Comments. The default, `jira`, attaches the screenshots to the ticket as before.

### What a project provides

The workflows read these from the project's checkout, at fixed paths: `.nvmrc`, `package.json` scripts (`typecheck`, `lint`, `test`, `fsd`, `dead-code`, `vendor-isolation`), `pnpm-lock.yaml`, `app.config.ts`, `eas.json`, `release-please-config.json` and `.release-please-manifest.json`, `vendors/<vendor>/vendor.json` and its `qa-notes.md` and `maestro/` folder, the Maestro flows (`.maestro/flows/`, or, when that folder is absent, one folder per feature, `.maestro/<feature>/`, where a folder whose name starts with `_` holds subflows and is not run on its own), the optional `.maestro/IMPACT`, and `scripts/agent-qa/instructions.md` (the QA agent's prompt). The shared scripts under `scripts/ci/` and `scripts/agent-qa/` are bundled with the actions and found through the `ci-scripts` action; a project does not carry them.

### Token safety

`device-checks`, `device-check-mode` and `jira-evidence-merge` hold the Claude and Jira tokens, so they fail their first job on any event but `pull_request`. Never trigger their callers from `pull_request_target` or `workflow_run`. The `release` and `hotfix-ota` callers hold store credentials: pin them to an exact tag (`@v1.2.3`) when the project wants a person to review each change to them, and require reviewers on `production-release`. A caller pinned to an exact tag pulls actions that match that tag.

## Versioning

Releases are exact tags (`v1.2.3`). `v1` is a floating major that moves to each compatible release, so a project gets CI fixes with no change. A breaking change ships as `v2`, and a project upgrades by changing its refs. A change is breaking when it adds a required input, removes or renames an input, changes a secret or an environment name, changes a check name, or changes a project-owned file the workflows read (see "What a project provides").

A release commit rewrites the internal references between workflows and actions to its own tag (`node scripts/set-ref.mjs <ref>`); on `main` they name `main`.

### Cutting a release

1. Start `tag-release` from `main` with the version `1.2.3-rc.1`. It tests, rewrites the references, and tags `v1.2.3-rc.1`. Nothing else moves.
2. Rehearse the candidate on a scratch project: point its callers at `@v1.2.3-rc.1`, set every documented input, and run its CI. A release that adds a required input is a new major.
3. When the rehearsal passes, start `tag-release` with `1.2.3` and `rehearsal-passed` set. It tags `v1.2.3` and moves `v1` to it.
4. To roll back, move `v1` back to the previous exact tag.

## Maintaining this repository

The owner sets these in the repository settings: a ruleset on `main` (pull request, code-owner review, no force-push, no bypass), a tag ruleset limiting `v*` tags to the maintainers team and the GitHub Actions app that runs `tag-release`, read-only default workflow permissions, approval required for every outside-collaborator workflow run, two-factor for members with write access, and a `release` environment with required reviewers and the secret `RELEASE_PUSH_TOKEN`, a fine-grained token (or GitHub App token) for this repository with contents write and workflows write (only the two push steps read it). A final release also needs its release candidate tag (`v1.2.3-rc.N`) to exist before `v1` moves. The release commit changes workflow files, which the built-in token cannot push. The repository's own workflows run on `pull_request` with a read-only token and GitHub-hosted runners, and `tag-release` is started by hand from `main` only.

`pnpm test` runs the script tests and the workflow-shape tests, `pnpm typecheck` checks them, and `pnpm lint:workflows` runs actionlint through Docker.

A project in another organisation must allow `Mobiweb-Studio/ci-workflows` and the third-party actions it uses in its Actions settings when it restricts which actions may run.
