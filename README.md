# ci-workflows

Reusable GitHub Actions workflows and actions for Mobiweb Expo projects. A project keeps thin caller files in its own `.github/workflows/` and calls the shared workflows here:

```yaml
jobs:
  ci:
    uses: Mobiweb-Studio/ci-workflows/.github/workflows/ci.yml@v1
```

The repository is public so that projects in other GitHub organisations can call it. It holds CI logic only: no app code, no docs and no secrets. Secrets and environments stay in each project.

## Using it

1. Copy the caller files from [`examples/callers/`](examples/callers) into the project's `.github/workflows/`. Keep each file's job id: a called job reports as `<caller job> / <shared job>`, so `ci` reports `ci / checks`, `ci / commits`, `ci / secret-scan` and `ci / ticket-key`, and the device gate waits for those names. Add the names you want to require to the main branch's ruleset.
2. Set the inputs. Every input and the token permissions the caller must grant are listed in the header comment of the workflow, and the caller examples already set them. A caller sets only inputs and secrets. It also owns its triggers, path filters, concurrency groups and token permissions. To change what a workflow does, add your own jobs in a separate workflow file; do not edit the steps of a shared one.
3. Give each caller job the permissions its example grants. A called workflow can only narrow the caller's token, so a caller that grants less fails at startup.
4. Create the repository secrets the callers pass by name: `CLAUDE_CODE_OAUTH_TOKEN` (the QA agent), `JIRA_API_TOKEN` (Jira evidence, only when used), `MS_TENANT_ID`, `MS_CLIENT_ID` and `MS_CLIENT_SECRET` (Jira evidence stored on OneDrive, only when used), `EXPO_TOKEN` and optionally `SENTRY_AUTH_TOKEN` (release and hotfix), optionally `RELEASE_PLEASE_TOKEN`, and optionally `NPM_AUTH_TOKEN` (for a project with private packages on GitHub Packages: `ci`, `device-checks`, `native-cache`, `ios-regression`, `release` and `hotfix-ota` set it in the environment of the jobs that run `pnpm install` and write `//npm.pkg.github.com/:_authToken=${NPM_AUTH_TOKEN}` to a user-level `.npmrc` under the runner's temp folder (emptied after each job, so a shared self-hosted runner's own `~/.npmrc` is never touched), because pnpm does not expand environment variables in the credentials of a project `.npmrc`; without it nothing changes), and optionally `MAESTRO_ENV` (the Maestro flows' variables, such as a test account for flows that sign in against a real backend: one `MAESTRO_<NAME>=<value>` per line, without quotes; `device-checks` and `ios-regression` give it to their Maestro jobs, and `device-checks` to the QA agent too; `scripts/ci/maestro-env.sh` masks each value in the log, exports the variables, and replaces the values with `***` in Maestro's debug output and reports and in the agent's output before they are uploaded, because those hold the typed text. The agent types a value with `qa-fill-secret <@ref|selector> <MAESTRO_NAME>` (`scripts/agent-qa/bin`), so it never sees it; the project's `scripts/agent-qa/instructions.md` or `qa-notes.md` tells it which variable to use). A caller job cannot declare an environment, and an environment's own secrets do not reach a called workflow, so these are repository secrets, readable by every workflow in the repository but not by fork pull requests. The shared jobs still declare the environments `qa-agent`, `jira-evidence` and `production-release`: create them in the project, and use their required reviewers and branch rules as the approval gates. `secrets: inherit` is not used, because it only works inside one organisation.

## The workflows

| Workflow | Caller job id | What it does |
|---|---|---|
| `ci.yml` | `ci` | Commit messages, secret scan, types, lint, tests, layout, dead code, and the Jira ticket key when asked. |
| `docs-check.yml` | `docs-check` | Requires docs for feature changes unless the PR has `no-docs`. |
| `human-review.yml` | `human-review` | Needs a person's approval of the head commit unless an agent review of it exists and the `needs-human-review` label was never applied. Off until a project's calibration is signed off: set `HUMAN_REVIEW_ENABLED` to `true`. |
| `device-check-mode.yml` | `device-check-mode` | Keeps one PR comment that says whether the two device checks run and why. |
| `device-checks.yml` | `device-checks` | Maestro and the QA agent on one shared APK, Maestro on an iOS simulator when asked, then the Jira evidence. |
| `native-cache.yml` | `native-cache` | Seeds the APK and build caches on main, and the iOS simulator app when asked. |
| `ios-regression.yml` | `ios-regression` | On a schedule on main, every Maestro flow on each iOS runtime asked for: tagged flows that fail, and untagged ones that pass. |
| `android-regression.yml` | `android-regression` | On a schedule on main (the example: every night), every Maestro flow on an Android emulator, `nightly` ones included. |
| `jira-evidence-merge.yml` | `jira-evidence-merge` | Attaches the last device-check screenshots to the Jira ticket when the PR merges, or stores them on OneDrive and links them. |
| `release.yml` | `release` | release-please, then the store build and submit when a release PR merges (`build: false` keeps only release-please). |
| `hotfix-ota.yml` | `hotfix` | A JS-only production update, started by hand. |

`ci` takes `fsd`, `dead-code` and `vendor-isolation`, true by default, for a project that declined that module; a step that is on and whose script is missing fails. `device-checks` also takes `maestro` and `qa-agent`, both true by default, so a project that declined a device check passes false and that check never runs. It also takes `qa-agent-model` (a Claude Code alias or model id), `qa-agent-max-turns` and `qa-agent-max-budget-usd`: `claude-sonnet-5-5`, 100 turns and $2 by default, from 1.21.0. The earlier defaults, `haiku`, 40 turns and $0.50, failed on a real project: a run stopped at the turn limit (`error_max_turns` at 41 turns, $0.21) with its check inconclusive, and Haiku typed the names of the `MAESTRO_*` variables into a login field instead of filling their values, then reported the test accounts broken (ICligo ADRs 0009 and 0026). A run's cost depends on its turns, not on the size of the diff: the fixed instructions cost about $0.04 before the first turn, and a run that checks something costs about $0.30 to $1.00 on Sonnet (68 turns cost $0.51 on Haiku, about $1.00 on Sonnet), so $2 lets a full 100-turn run finish while still capping a runaway one. A project that wants more room passes a higher ceiling (ICligo passes $5), and one that wants the cheaper model passes `haiku` and lower limits; record the measured turns and cost of the first runs and set the ceiling to about twice the worst one. The `qa-agent` artifact keeps the agent's whole run, each command and its output, in `qa-claude-transcript.jsonl`, with the `MAESTRO_ENV` values replaced by `***`. The report fails as a tooling failure, whatever the agent says, when the transcript shows a sign-in that cannot have happened: the agent typed a `MAESTRO_*` name with `agent-device` instead of filling its value with `qa-fill-secret`, or `qa-fill-secret` failed. Every workflow takes a `runner` input. The jobs that build, test or run the app default to `ubuntu-latest`, a GitHub-hosted runner; a project passes its own label for other runners, and the emulator jobs need KVM and a large disk, or a self-hosted Apple Silicon Mac (below). Every Android emulator (`maestro-android`, `qa-agent` and `android-regression`) is created with the `pixel_6` hardware profile, a 1080x2400 screen at 420 dpi on API 34; without a profile the emulator got Android's default 320x640 screen at 160 dpi, where a screen's lower buttons sat under the app's tab bar and flows that pass on a phone timed out. `device-checks` (its `maestro-android` job; the QA agent keeps `pixel_6`) and `android-regression` take `android-profile`, `pixel_6` by default: empty gives that default 320x640 screen, the size of EAS's Android emulator, so a project whose client runs the flows on EAS passes `android-profile: ""` to its regression, or to a check it runs before it hands a release over, and finds a flow that fails on the short screen before the client does (ICligo's 0.14.0 release failed there, PR #417). `device-checks`, `android-regression` and `ios-regression` take `maestro-version`, `2.10.0` by default, for the same reason: a project whose client runs another Maestro (EAS Workflows ran 2.6.1, which lacks commands 2.10 has on iOS) passes that version. Maestro is installed in each job's `RUNNER_TEMP` (`scripts/ci/install-maestro.sh`), not with its own installer, which writes to `~/.maestro` and the shell profiles: on a shared Mac one job's install deleted the CLI under another job still running its flows. The jobs that only read, wait or comment have a runner input of their own, so a project can send them to cheaper or more numerous runners (ICligo: the M3's light runners): `commits`, `secret-scan` and `ticket-key` in `ci`, and `changes`, `gate`, `ios-app-link` and `jira-evidence` in `device-checks`, through a `light-runner` input; `device-check-mode`, `docs-check`, `human-review` and `jira-evidence-merge` through their `runner` default. A project that cannot use GitHub-hosted runners passes its own label to both.

`device-checks` runs only the Maestro flows a change affects when the project has `.maestro/IMPACT`: one line per rule, as in CODEOWNERS, a path glob from the repository root and the flow tags a change there affects (`src/pages/login/** login`; a tag `*` means every flow). The flows tagged `smoke` always run. Every flow runs when the project has no map or when a changed app file matches no line, so the map can narrow a run but never hide a change it does not know. A story PR (label `us`) runs the flows tagged `smoke` and the flows tagged with its story's code, read from the `## Ticket` section of the PR's description (`US-21`), whatever the map says; the nightly regression runs the rest. A story PR with no code there runs every flow. The mode comment names the tags. Flows tagged `nightly` run only in the regression workflows. Each flow writes its screenshots to `maestro-output/<flow>/`, and the evidence on OneDrive names the files `android/<flow>/…` and `ios/<flow>/…`, beside a `summary.md` with each flow's result. `run-maestro.sh` lists the flows it ran in `maestro-output/flows.tsv`, and the Jira comment turns that into a table: each flow's `name:` linked to its file at the PR's head, its result on Android and iOS, and the acceptance criteria its tags name, written `<KEY>-AC<n>` (such as `ICLIGO-22-AC4`, shown as "ICLIGO-22 AC 4").

`device-checks` also takes `ios-runner`, empty by default. When a project names a runner there (a JSON array of labels for a self-hosted Mac, such as `'["self-hosted","macOS","ARM64","ios"]'`, or a hosted label such as `macos-15`), the `maestro-ios` job gets the app for the iOS simulator on it, runs the flows whose config has the tag `ios` on a simulator made for the job, keeps its report and screenshots as the artifact `maestro-ios` for `ios-retention-days` (3 by default, because each run uploads about 90 MB and a few days of PRs filled the organization's artifact storage; the evidence that lasts is the Jira comment and its OneDrive folder), and keeps the zipped simulator app as the artifact `ios-simulator-app` for 7 days; the `ios-app-link` job then comments its link on the PR, so a reviewer with a Mac can open the PR in the Simulator. The app is built for the simulator ad-hoc signed (the identity `-`, no certificate or Apple account), so it carries the entitlements prebuild generates and can use the Keychain, as `expo-secure-store` needs. Like the APK, the app is repacked with the PR's JS (about 25 seconds) when a cached app has the same native fingerprint, and built when none has; a repacked app is signed again ad-hoc with the same entitlements: pass the same `ios-runner` to `native-cache`, whose `seed-ios` job fills that cache from main. When `jira-evidence` is on, the Jira comment gives the iOS verdict too, and the screenshots of a failed iOS run. The runner needs Xcode, CocoaPods and Java 17, and a GUI session for the simulator. The job runs only for PRs from the same repository, and its only secrets are the optional `MAESTRO_ENV` (redacted from Maestro's output, so none stays on the Mac's disk) and the optional `NPM_AUTH_TOKEN`, which the job writes to a user-level `.npmrc` under the runner's temp folder (emptied after each job), never to the Mac's own `~/.npmrc`. The caller example passes the repository variable `IOS_RUNNER`. `ios-regression` runs on the same runner on a schedule: every flow, tagged or not, on each runtime in its `runtimes` input (installed on the runner), one at a time, and keeps each runtime's report and screenshots as `ios-regression-<runtime>` for `retention-days` (3 by default). A flow tagged `ios` that fails fails the run; an untagged one that passes is listed in the summary as one to tag. It refuses any event but `schedule` and `workflow_dispatch`, so pull request code never reaches the runner through it. Both regressions take `timeout-minutes`, 150 by default from 1.21.0 (90 before): the build and every flow must finish within it, or the job is cancelled with no verdict. ICligo's 61 flows take 75 to 100 minutes on a Mac shared with the PR checks, so at 90 most nights were cancelled; a project whose suite takes longer still raises it. In `device-checks` the build (`apk`, 45 minutes) is its own job, so `maestro-android` (100 minutes) and `maestro-ios` (120) hold only the flows, about a minute each.

`device-checks`, `native-cache`, `android-regression` and `ios-regression` take `app-env`, empty by default. A project whose app config reads `APP_ENV` (ICligo: `dev`, `staging` or `prod`, unset meaning `prod`) passes the environment its flows' test users and backend belong to, such as `app-env: dev`, and the same value to all four, because the cached APK and simulator app are keyed by it (`device-apk-v1-x86_64-default.dev-…`): a dev app never serves a prod run, and a `native-cache` seeded for another environment is never used. The app is built, and repacked, with `APP_ENV` set to it; empty leaves `APP_ENV` unset, so the app builds as before and the keys of the apps already cached do not change. `CRASH_REPORTING=off`, `SENTRY_DISABLE_AUTO_UPLOAD=true` and `AUTH_SOURCE=mock` stay set whatever the environment. `APP_ID`, the id Maestro and the QA agent launch, comes from the resolved Expo config (`expo config --json` with `APP_VARIANT` and `APP_ENV` set: `android.package` or `ios.bundleIdentifier`), not from `vendor.json`, so it carries the environment's suffix (`.dev`). The same config gives `APP_SCHEME`, the app's URL scheme (the platform's own `scheme` or the top-level one), which the flows read as `${APP_SCHEME}` for deep links when the app has one.

### A self-hosted Mac

Which runner each job uses comes from three inputs. Set each one from a repository (or organisation) variable in the callers, such as `${{ vars.ANDROID_RUNNER || 'ubuntu-latest' }}`, so a project moves its CI between runners by changing a variable, not every caller.

| Input | Jobs | Default | Needs | Empty |
|---|---|---|---|---|
| `runner` | Every job that builds, tests or runs the app: `ci`'s checks, `apk`, `maestro-android`, `qa-agent`, `android-regression`, `native-cache`, `release`, `hotfix-ota`; and the whole of `device-check-mode`, `docs-check`, `human-review` and `jira-evidence-merge` | `ubuntu-latest` | Emulator jobs: Linux with KVM and a large disk, or an Apple Silicon Mac with the Android SDK, one emulator job at a time | The job cannot start |
| `light-runner` | Jobs that only read, wait or comment: `commits`, `secret-scan`, `ticket-key` (`ci`); `changes`, `gate`, `ios-app-link`, `jira-evidence` (`device-checks`) | `ubuntu-latest` | Nothing beyond the basics; many instances can share one Mac | The job cannot start |
| `ios-runner` | `maestro-ios` (`device-checks`), `seed-ios` (`native-cache`), `ios-regression` | empty | A Mac with Xcode, CocoaPods, Java 17 and a GUI session | The iOS jobs are skipped |

**A persistent runner.** A self-hosted runner keeps its home folder and its checkout between jobs, and several instances on one Mac share the same user. So a step must never leave anything behind that the next job reads. The shared workflows follow these rules; a project's own workflows on the same runner must too:

- Tokens go to a job-only file under `RUNNER_TEMP` (`NPM_CONFIG_USERCONFIG=$RUNNER_TEMP/npmrc`), never to `~/.npmrc`, `~/.netrc` or a global git config. The runner empties `RUNNER_TEMP` after each job.
- Tools a job installs go under `RUNNER_TEMP` too (pnpm, Maestro), so two jobs at once do not install over each other.
- A job that commits clears the hooks another job's install left in the checkout (`git -c core.hooksPath=/dev/null commit …`), as a fresh GitHub-hosted checkout would have none. ICligo's translations bot ran a commit-msg hook without its dependencies and failed.
- Scripts run on macOS's `/bin/bash` 3.2 and BSD tools: no `mapfile`, associative arrays, `sed -i`, `grep -P` or `date -d`. `scripts/ci/portable-shell.test.ts` checks this repository's scripts and steps; a project can copy it for its own.

Every job also runs on a self-hosted Apple Silicon Mac, so a project can keep all of its CI on one machine. The Android jobs see `runner.arch == 'ARM64'` and build and test for `arm64-v8a`: build-android-apk compiles that architecture and skips the Linux disk cleanup, the APK's cache key names it (`device-apk-v1-arm64-v8a-…`, never shared with an `x86_64` APK), the emulator runs that system image on macOS's own hypervisor, and the KVM step runs only on Linux. `secret-scan` runs the `gitleaks` binary when the runner has no Docker. The Mac needs, for the runner's user: Node and pnpm through corepack, Java 17, `gh`, `jq`, `ccache` and `gitleaks` 8.30 or later on the `PATH` (Homebrew), and the Android SDK with `ANDROID_HOME` (and `ANDROID_SDK_ROOT`) in the runner's environment, its licenses accepted and `platform-tools`, `emulator`, a platform, build tools and `system-images;android-34;default;arm64-v8a` installed. The emulator jobs listen on the emulator's default port, so a Mac runs one of them at a time: give `runner` a label that only one runner instance on the Mac carries. The light jobs need no GUI session and can run on any number of instances; `maestro-ios` needs one (see above).

`device-checks` and `jira-evidence-merge` post the Jira evidence to the ticket in the branch name by default. A project that tracks its device checks on a QA sub-task of each story passes `jira-evidence-target: qa-subtask` to both. The poster then reads the branch's ticket, takes its parent when it is a sub-task, and posts the comment and screenshots to the story's one sub-task with the label in `jira-qa-label` (`qa` by default). When the story has no such sub-task, or more than one, or Jira cannot be read, the evidence goes to the branch's ticket and the job shows a warning that names the reason. The Jira account needs no more than before (Browse Projects, Add Comments, Create Attachments): a person makes the QA sub-task, and the poster never creates or edits an issue.

Choose the storage when a project starts, not when Jira fills up. Each device-check run attaches its screenshots, so a project that runs device checks on most pull requests outgrows a Jira site's attachment storage within weeks (ICligo filled it in two), and attachments moved later stay split across the two places. So `onedrive` is the recommended choice for any project with a regular QA cadence; `jira` suits a project with few device-check runs or no SharePoint. A project whose Jira site is short of attachment storage, or that follows that advice, passes `jira-evidence-storage: onedrive` to both, with `onedrive-drive-id` (a SharePoint or OneDrive document library's drive id) and `onedrive-folder` (the folder in it, such as `ICligo/QA evidence`), and the secrets `MS_TENANT_ID`, `MS_CLIENT_ID` and `MS_CLIENT_SECRET`. The poster then gets a Microsoft Graph token with the client-credentials flow and uploads the screenshots and `qa-report.json` of every run, passing runs too, to `<folder>/<story>/<ticket>/<YYYY-MM-DD HH-MM> PR-<n> passed|failed/` (the time in UTC, ` attempt <k>` added on a re-run), and on merge to `<YYYY-MM-DD HH-MM> PR-<n> merged/`, so a story's runs sort by date. Maestro's screenshots are stored as `android/<flow>/<file>` and `ios/<flow>/<file>`, without Maestro's own timestamp and screenshot folders. A file over 4 MiB goes through an upload session. The comment links the folder with a view-only link for the organization, never an anonymous one, or with the folder's own address and a warning when the tenant refuses such links. Every Microsoft failure is a warning too: the comment is still posted and says the evidence could not be stored, and the poster does not fall back to Jira attachments. The app registration needs only the application permission `Sites.Selected`, with the `write` role granted on the one site by a SharePoint administrator, never `Files.ReadWrite.All` or `Sites.ReadWrite.All`. The Jira account then needs only Browse Projects and Add Comments. The default, `jira`, attaches the screenshots to the ticket as before.

### What a project provides

The workflows read these from the project's checkout, at fixed paths: `.nvmrc`, `package.json` scripts (`typecheck`, `lint`, `test`, `fsd`, `dead-code`, `vendor-isolation`), `pnpm-lock.yaml`, `app.config.ts`, `eas.json`, `release-please-config.json` and `.release-please-manifest.json`, `vendors/<vendor>/vendor.json` and its `qa-notes.md` and `maestro/` folder, the Maestro flows (`.maestro/flows/`, or, when that folder is absent, one folder per feature, `.maestro/<feature>/`, where a folder whose name starts with `_` holds subflows and is not run on its own), the optional `.maestro/IMPACT`, and `scripts/agent-qa/instructions.md` (the QA agent's prompt). The shared scripts under `scripts/ci/` and `scripts/agent-qa/` are bundled with the actions and found through the `ci-scripts` action; a project does not carry them.

### Token safety

`device-checks`, `device-check-mode` and `jira-evidence-merge` hold the Claude and Jira tokens, so they fail their first job on any event but `pull_request`. Never trigger their callers from `pull_request_target` or `workflow_run`. The `release` and `hotfix-ota` callers hold store credentials: pin them to an exact tag (`@v1.2.3`) when the project wants a person to review each change to them, and require reviewers on `production-release`. A caller pinned to an exact tag pulls actions that match that tag.

### Runner capacity

A project with one self-hosted Mac runs its device jobs one at a time: the emulator jobs share the emulator's port, and `maestro-ios` needs the one GUI session. Plan for it:

- **Jobs run serially.** A full Maestro run of about 60 flows takes over an hour, and every PR check, regression and release build waits behind it. Narrow PR runs with `.maestro/IMPACT` and story tags (above), and leave the full suite to the nightly regression.
- **Release runs can queue for hours.** release-please reads `main` through the API when its job starts, not when it was queued, so a late run can find the release already made. Give the release and the long jobs their own `concurrency` group (`cancel-in-progress: false` for releases and regressions; `true` for PR checks, so a new push cancels the superseded run), pass `build: false` to `release` when the store build runs elsewhere, or give those jobs a runner of their own.
- **Schedule crons off the hour** (`17 2 * * *`, not `0 2 * * *`): GitHub's scheduler is busiest on the hour, and a regression that starts late runs into the next morning's PR checks.
- **Scheduled runs can fire hours late, or not at all,** when GitHub's queue is busy. Do not chain jobs on a schedule's start time; read the run's own result, and start a missed regression by hand with `workflow_dispatch`.
- **When the Mac is off, jobs wait** in the queue until it is back (GitHub cancels a job that waits 24 hours). Keep the light jobs (`light-runner`) on their own runner instances, so a long device run does not hold up the checks that only read or comment.

## Versioning

Releases are exact tags (`v1.2.3`). `v1` is a floating major that moves to each compatible release, so a project gets CI fixes with no change. A breaking change ships as `v2`, and a project upgrades by changing its refs. A change is breaking when it adds a required input, removes or renames an input, changes a secret or an environment name, changes a check name, or changes a project-owned file the workflows read (see "What a project provides"). A changed default is not breaking, because a project that passes the input keeps its value, but every project that relies on the default inherits the change: it ships as a minor release, its pull request lists each one under "Changed defaults" with the old value a caller passes to keep it, and this README names the release it changed in.

A release commit rewrites the internal references between workflows and actions to its own tag (`node scripts/set-ref.mjs <ref>`); on `main` they name `main`.

### Cutting a release

1. Start `tag-release` from `main` with the version `1.2.3-rc.1`. It tests, rewrites the references, and tags `v1.2.3-rc.1`. Nothing else moves.
2. Rehearse the candidate on a scratch project: `node scripts/rehearse.mjs open <owner/repo> v1.2.3-rc.1` points every reference its workflows make to this repository at the candidate on a branch, opens a pull request labelled `rehearsal` and titled "do not merge", and with `--dispatch android-regression.yml` (repeatable) also starts a workflow that never runs on a pull request. When its checks finish (`gh pr checks <url> --watch`), `node scripts/rehearse.mjs close <owner/repo> <number>` comments the result, closes the pull request, deletes the branch and prints the line to keep. A release that adds a required input is a new major.
3. When the rehearsal passes, start `tag-release` with `1.2.3` and `rehearsal-passed` set. It tags `v1.2.3` and moves `v1` to it. To release without a rehearsal, leave `rehearsal-passed` unset and write why in `skip-rehearsal-reason` (such as "README only" or "defaults only, no step changed"); `v1` moves too. The release candidate tag must exist either way. The release tag is annotated and its message says which it was (`git tag -l --format='%(contents)' v1.2.3`), so a skip is never silent. Skip only a release that changes no step that runs: a change to a script, an action or a job's steps is rehearsed.
4. To roll back, move `v1` back to the previous exact tag.

## Maintaining this repository

The owner sets these in the repository settings: a ruleset on `main` (pull request, code-owner review, no force-push, no bypass), a tag ruleset limiting `v*` tags to the maintainers team and the GitHub Actions app that runs `tag-release`, read-only default workflow permissions, approval required for every outside-collaborator workflow run, two-factor for members with write access, and a `release` environment with required reviewers and the secret `RELEASE_PUSH_TOKEN`, a fine-grained token (or GitHub App token) for this repository with contents write and workflows write (only the two push steps read it). A final release also needs its release candidate tag (`v1.2.3-rc.N`) to exist before `v1` moves. The release commit changes workflow files, which the built-in token cannot push. The repository's own workflows run on `pull_request` with a read-only token and GitHub-hosted runners, and `tag-release` is started by hand from `main` only.

`pnpm test` runs the script tests and the workflow-shape tests, `pnpm typecheck` checks them, and `pnpm lint:workflows` runs actionlint through Docker. Run `pnpm test` on a Mac before merging a change to a shell script: its `/bin/bash` is 3.2, as on the self-hosted runners, while this repository's own CI runs bash 5.

A change to `release`, `hotfix-ota` or any job that pushes, publishes or syncs to another repository merges only after a dry run: point a scratch project's caller at the pull request's branch (`@<branch>`), add `workflow_dispatch` to that caller's triggers and start it by hand (for `release`, with `build: false` when the store build is not what changed), and link the run in the pull request. Those paths run only after a merge, so their failures otherwise reach a project first (ICligo: a sync that stopped at `mapfile`, a release that never built, PRs #361 and #454).

A project in another organisation must allow `Mobiweb-Studio/ci-workflows` and the third-party actions it uses in its Actions settings when it restricts which actions may run.
